# Personal Finance Intelligence System

## Product Summary

A privacy-first web application that helps individuals track, understand, and improve their finances.

Users can record transactions manually or import them through CSV files. The application then provides insights into spending, budgets, goals, net worth, recurring expenses, and investments.

## Target Customer

An individual who earns a regular income and uses multiple bank, savings, credit, or investment accounts but does not have one clear view of their financial situation.

## Main Problem

Users struggle to answer:

- Where is my money going?
- Am I staying within my budget?
- How much can I save every month?
- Will I reach my financial goals?
- How is my net worth changing?
- Are recurring expenses affecting my finances?
- Are my investments performing well?

## Main Value Proposition

The application helps users understand their complete financial position and make better decisions using data they control.

## Privacy Position

Version 1 will not use live bank integrations or store bank credentials.

Users will provide data through:

- Manual transaction entry
- CSV transaction import

## Core Product Loop

TRACK -> UNDERSTAND -> PLAN -> ACT -> MEASURE -> IMPROVE

## Primary User Workflows

### 1. Register and Set Up

1. The user creates an account and signs in.
2. The user creates their financial accounts, such as salary account, savings account, credit card, cash, or investment account.
3. The user enters the opening balance for each account.
4. The user reviews the default transaction categories.

### 2. Add Financial Activity Manually

1. The user selects an account.
2. The user enters the transaction date, amount, type, description, and category.
3. The system validates the input and saves the transaction.
4. The account balance and relevant analytics are updated.
5. The user can edit or delete the transaction later.

### 3. Import Transactions from CSV

1. The user selects an account and uploads a CSV file.
2. The system previews the detected columns and sample rows.
3. The user maps CSV columns to date, amount, description, and category.
4. The system validates each row and reports invalid or duplicate rows.
5. The user confirms the import.
6. The system saves only the confirmed valid transactions.

### 4. Understand Spending

1. The user opens the spending dashboard.
2. The system groups transactions by month and category.
3. The user compares income, expenses, and transfers.
4. The user filters the results by account, date range, or category.
5. The user can open a category to inspect the underlying transactions.

### 5. Create and Review a Budget

1. The user chooses a month and spending category.
2. The user sets a planned amount.
3. The system compares the budget with actual categorized expenses.
4. The system shows the remaining amount or overspending.
5. The user can adjust the budget for a future month.

### 6. Track a Financial Goal

1. The paid user creates a goal, such as buying a bike.
2. The user enters the target amount, current contribution, and target date.
3. The system calculates the required monthly contribution.
4. The user records contributions or links them to eligible transactions.
5. The system shows progress, projected completion date, and whether the user is ahead or behind.
6. The system provides explainable savings suggestions based on income, expenses, and recent savings behavior.

### 7. Review Net Worth and Investments

1. The user records asset and liability account balances.
2. The system calculates net worth as total assets minus total liabilities.
3. The user records investment contributions, withdrawals, and valuations.
4. The system displays investment performance over time.
5. The system calculates investment returns using dated cash flows and XIRR where applicable.

### 8. Review Recurring Expenses

1. The system looks for similar transactions occurring at regular intervals.
2. The user reviews the possible recurring transactions.
3. The user confirms, edits, or dismisses each suggestion.
4. Confirmed recurring expenses appear in spending and planning views.

## Important Workflow Rules

- Every financial record belongs to exactly one user.
- A user must never be able to read or modify another user's data.
- Transfers between a user's accounts must not be counted as income or expense.
- Imported rows must be validated before they change account balances or analytics.
- Financial calculations must use exact decimal amounts rather than floating-point money values.
- Automated categorization and suggestions must be reviewable and correctable by the user.
- Goal suggestions are guidance, not guaranteed financial advice.

## Functional Requirements

### Authentication and Data Ownership

- A user can register, sign in, and sign out.
- A user can access only their own financial data.
- Unauthenticated requests to protected resources are rejected.

### Accounts and Transactions

- A user can create, view, update, and archive financial accounts.
- A user can create, view, update, and delete their own transactions.
- A transaction has a date, amount, type, description, account, and category where applicable.
- The system supports income, expense, and transfer transactions.
- Transfers can connect two accounts owned by the same user.

### CSV Import

- A user can upload a CSV file for a selected account.
- The system shows a preview before importing data.
- The system reports malformed, incomplete, and duplicate rows.
- The user must confirm a valid import before transactions are saved.
- A failed import must not partially corrupt existing financial data.

### Budgets and Analytics

- A user can create a monthly budget for a category.
- The system calculates actual spending from categorized expense transactions.
- The system displays budgeted amount, actual amount, remaining amount, or overspending.
- A user can filter analytics by date range, account, and category.

### Goals

- A paid user can create, update, pause, and complete a financial goal.
- A goal has a name, target amount, current amount, and target date.
- The system calculates required contributions and progress percentage.
- The system recalculates projections when relevant income, expense, or contribution data changes.
- The system explains the inputs behind each savings suggestion.

### Net Worth and Investments

- The system calculates net worth from asset and liability balances.
- A user can record investment cash flows and valuations.
- The system calculates investment performance using dated cash flows.
- The system uses XIRR for irregularly timed investment cash flows.

### Recurring Transactions

- The system can identify possible recurring transactions from transaction history.
- A user can confirm, edit, or dismiss a recurring-transaction suggestion.
- Confirmed recurring transactions can be included in planning and analytics.

## Non-Functional Requirements

### Security and Privacy

- Passwords must be stored only as secure password hashes.
- Secrets and database credentials must come from environment-based configuration.
- Every protected query must enforce the authenticated user's ownership.
- Sensitive values must not appear in application logs or error messages.
- The application must validate uploaded files and reject unsafe or unsupported input.

### Correctness

- Money values must use exact decimal arithmetic.
- Date and timezone behavior must be explicit and consistent.
- Financial calculations must be covered by tests for normal and edge cases.
- A failed write or CSV import must leave existing data unchanged.

### Reliability and Usability

- API errors must return consistent, useful responses without exposing internals.
- Important write operations should be safe to retry where practical.
- The API must provide clear validation errors for users and frontend developers.
- The application must expose a health-check endpoint for deployment monitoring.

### Performance

- List endpoints must support pagination before large datasets become a problem.
- Common queries must use appropriate database indexes.
- Analytics queries must be measured with realistic sample data before deployment.

## MVP Success Criteria

- A new user can complete setup and create at least one financial account without assistance.
- A user can record a transaction manually and see it in the correct account and analytics results.
- A user can import a representative CSV file, review validation results, and confirm the import without duplicate transactions.
- Spending analytics reconcile with the underlying transactions for a selected month and category.
- A user can compare a budget with actual spending and identify remaining budget or overspending.
- A user can create a goal and understand the amount, progress, required contribution, and projected completion date.
- Net worth equals total assets minus total liabilities for representative account data.
- Investment-return results are correct for test cases with irregular cash-flow dates.
- A user cannot access another user's accounts, transactions, goals, or analytics, including by changing an object ID in a request.
- The application can run locally from documented setup instructions and reports whether its database dependency is healthy.

## Initial Domain Glossary

### User

The person who owns the data in the application. A user may have multiple financial accounts, transactions, budgets, goals, and investments. The user record stores authentication and profile metadata, not financial balances.

Suggested fields:
- user_id
- email
- password_hash
- created_at
- updated_at
- last_login_at

### Account

A place where money is held or owed, such as a bank account, savings account, credit card, cash wallet, loan, or investment account. The account row stores metadata, while the current balance is derived from the account's transactions and opening balance.

Suggested fields:
- account_id
- user_id
- name
- account_type
- currency
- is_active
- created_at
- updated_at

### Transaction

A dated financial event that changes an account's balance. The business meaning is tracked separately from the payment method. A transaction is an income, expense, or transfer. Payment method such as card, UPI, cash, or bank transfer should be stored separately.

Suggested fields:
- transaction_id
- user_id
- account_id
- category_id
- description
- amount
- transaction_kind
- payment_method
- transaction_date
- created_at

### Category

A label used to group transactions, such as salary, rent, groceries, or transport. Categories make budgets and spending analytics possible. A category may be hierarchical using a parent-child relationship.

Suggested fields:
- category_id
- user_id
- name
- parent_id
- category_type
- created_at

### Budget

A planned spending amount for a category during a defined period, such as a month. A budget is compared with eligible expense transactions in that period. The remaining amount is derived, not stored as a permanent column.

Suggested fields:
- budget_id
- user_id
- category_id
- amount
- start_date
- end_date
- created_at

### Goal

A planned financial target with a target amount and date, such as saving ₹4,00,000 for a bike. Progress represents money intentionally assigned to that goal, not merely money sitting in every account.

Suggested fields:
- goal_id
- user_id
- name
- target_amount
- target_date
- current_amount
- created_at

### Asset and Liability

An asset is something the user owns that has financial value, such as cash or investments. A liability is money the user owes, such as a credit-card balance or loan. Net worth is calculated as assets minus liabilities.

### Investment and Holding

An investment is an activity involving financial assets. A holding is the user's current position in a specific investment, such as 10 shares of a company or units of a mutual fund. Current value can be computed with units multiplied by current price.

### Recurring Transaction

A transaction pattern that repeats with similar details at a regular interval, such as monthly rent or a subscription. The rule should be stored once and future occurrences generated from it, not stored as one row per month.

Suggested fields:
- recurring_transaction_id
- user_id
- account_id
- description
- expected_amount
- frequency
- next_expected_date
- category_id
- created_at

## Initial Entity Relationships

- One user owns many accounts, transactions, budgets, goals, and investments.
- One account has many transactions.
- A transaction belongs to one account and may belong to one category.
- A transfer is represented as two transactions in the MVP: one debit on the source account and one credit on the destination account.
- A budget belongs to one user, one category, and one period.
- A goal belongs to one user and tracks a saved contribution amount.
- An investment belongs to one user and may have many holdings and cash-flow records.
- A recurring-transaction rule belongs to one user and may generate many future transaction instances.
- Category may support self-referencing parent-child relationships for hierarchical grouping, such as Food -> Groceries and Transport -> Fuel.

## Initial Domain Invariants

- Every owned record has exactly one user owner.
- A transaction amount is greater than zero; its kind determines whether it is income, expense, or transfer.
- A transaction date is required and cannot be interpreted differently across reports.
- An income transaction belongs to one account and increases that account's balance.
- An expense transaction belongs to one account and decreases that account's balance.
- A transfer must debit one account and credit another account owned by the same user.
- A transfer must not affect income totals, expense totals, or spending-category totals.
- A budget period and category combination must not create competing active budgets for the same user.
- A goal target amount is greater than zero, and its target date is after its creation date.
- Goal progress cannot be negative or greater than the target amount.
- A user cannot create a transaction against an archived account.
- Deleting or editing a transaction must cause all derived totals and projections to be recalculated consistently.
- Payment method and financial meaning are separate values and should not be conflated.

## Domain Decisions Resolved

- Account balances are derived from transactions plus opening balance; they are not blindly stored as mutable fields.
- Goal contributions are explicit amounts assigned to the goal, and they may optionally be linked to transactions later.
- A transaction has one category in the MVP, not multiple categories.
- Credit-card payments are represented as transfers between accounts, with the original purchase as the expense.
- Investment holdings are separate records connected to the investment or account structure.
- The MVP supports one configured currency per user and stores timestamps in UTC with a separate local reporting timezone.
- Categories may include a parent-child self-reference for hierarchical grouping.
- Budget remaining amount is derived rather than stored.
- Recurring transactions are stored as rules and generated into future transactions as needed.

## Phase 2: System Architecture

### Architecture Style

The backend will be a modular monolith: one deployable FastAPI application and one PostgreSQL database, organized into modules by business capability. Modules share the database and run in one process, but their responsibilities and public interfaces remain explicit.

This is appropriate for the MVP because it keeps deployment and debugging simple while preventing the codebase from becoming one unstructured collection of routes.

### Backend Modules

- `auth`: registration, login, password hashing, and authenticated-user context.
- `users`: user profile and preferences such as currency and reporting timezone.
- `accounts`: account types, opening balances, archival, and account ownership.
- `transactions`: income, expense, transfer, validation, and CSV import.
- `categories`: default and user-defined transaction categories.
- `budgets`: monthly category plans and budget-versus-actual calculations.
- `goals`: paid goal access, contributions, projections, and explainable suggestions.
- `analytics`: spending summaries, trends, and net-worth calculations.
- `investments`: holdings, valuations, cash flows, and XIRR calculations.
- `recurring`: recurring-transaction detection and user confirmations.

Each module may contain API routes, schemas, domain logic, and database access for its capability. Shared code is limited to cross-cutting concerns such as configuration, authentication dependencies, database sessions, and error handling.

### Frontend and Backend Boundary

The separate web frontend communicates with the backend through JSON REST APIs over HTTPS.

- The frontend owns presentation, navigation, and form interaction.
- The backend owns authentication, authorization, validation, business rules, calculations, and persistence.
- The backend returns response schemas designed for frontend use rather than exposing raw database models.
- OpenAPI generated by FastAPI is the initial API contract.

### Request and Data Flow

1. A request reaches a versioned resource route.
2. Authentication identifies the user when the resource is protected.
3. The route validates input using a Pydantic request schema.
4. Domain logic checks business rules and ownership.
5. A repository or query function reads or writes through a SQLAlchemy session.
6. The database commits the transaction or rolls it back on failure.
7. The route returns a Pydantic response schema and an appropriate HTTP status.

For CSV imports, validation and preview happen before the confirmation write. The confirmed batch is saved in one database transaction so it cannot partially import.

### Configuration

- Configuration is loaded from environment variables using a typed settings object.
- Local development may use a `.env` file that is excluded from version control.
- Required settings include database URL, authentication configuration, application environment, and allowed frontend origins.
- Secrets are never hard-coded or committed.

### Error Handling

- Validation errors return a consistent client-error shape with field details where applicable.
- Missing or unauthorized resources do not reveal whether another user's record exists.
- Domain conflicts, such as duplicate imports or an archived account, return a clear conflict or validation response.
- Unexpected exceptions are logged with a request identifier and returned as a generic server error.

### Logging and Health

- Logs use structured fields such as level, timestamp, request identifier, route, and status code.
- Logs exclude passwords, tokens, full CSV contents, and unnecessary financial details.
- A health endpoint reports application availability.
- A readiness check verifies the database connection separately from basic process health.

### Initial Technical Decisions

- Python and FastAPI for the HTTP application.
- Pydantic for request and response validation.
- SQLAlchemy for database access while retaining understanding of the SQL it represents.
- PostgreSQL as the primary database.
- Alembic for versioned database migrations.
- Pytest for unit, integration, and API tests.
- Synchronous request handling for the MVP; background jobs are not justified yet.
- REST resources rather than GraphQL or microservices.
- No Redis, message broker, or live bank integration in Version 1.


## Paid Features

- Goal tracking and progress projections
- Personalized savings suggestions
- Goal completion-date predictions

- Recurring spending insights
- Historical financial comparisons
- More detailed reports

## Goal Tracking Example

A user wants to buy a bike.

- Monthly income: ₹50,000
- Bike cost: ₹4,00,000
- Current savings: ₹50,000
- Target date: 12 months

The application calculates:

- Remaining amount: ₹3,50,000
- Required monthly saving: approximately ₹29,167
- Current progress percentage
- Actual amount saved each month
- Whether the user is ahead or behind
- Expected completion date

Example suggestion:

"You saved ₹22,000 this month. To reach your target in 12 months, you need to save approximately ₹29,167 per month. You are currently ₹7,167 behind schedule."

## Intelligence Approach

We will start with deterministic, explainable rules instead of ML.

The first version will:

1. Calculate income and expenses.
2. Estimate monthly surplus.
3. Calculate the required monthly saving.
4. Compare planned and actual savings.
5. Project the completion date.
6. Generate rule-based suggestions.

ML may be added later if we have enough user data and can prove that it performs better than the rule-based approach.

Possible future ML capabilities:

- Predicting the probability of reaching a goal
- Estimating realistic monthly savings
- Identifying spending categories that can be reduced
- Recommending a better target date
- Detecting unusual spending patterns
